# テーマ選定の記録

最終更新: 2026-09-20

建設DX × Web開発の個人開発テーマとして10案を比較検討した記録。
結論は **案B: 図面リビジョン管理 + 差分検出 + 指摘管理**。

---

## 選定基準

「機能が面白いか」ではなく **作る過程で何を考え、何を経験できるか**。

そこから導かれる実質的な基準は3つ:

- **重いもの**を扱うか → 非同期・キュー・ワーカーが必然になるか
- **大きいもの**を扱うか → ファイル管理・ストレージ・パフォーマンス設計が出るか
- **複数人が同時に触るか** → 認可・楽観的ロック・リアルタイムが出るか

## 当初案（A）の客観的評価

良い題材ではある。座標処理・ファイル・認可が自然に出るし、
是正フローは建設DXの中核業務なのでテーマとしての説得力も高い。

**ただし弱点がある:**

- コアは結局 `Issue` テーブルのCRUD。座標が付くだけ
- **バックグラウンド処理の必然性が薄い**（サムネ生成くらい）
- データ量が小さく、インデックス設計やページング設計の「痛み」を体験しづらい
- リアルタイム通信も「あると嬉しい」止まりで、なくても成立する

→ **技術を後付けしないと学習項目が埋まらない。**
後付けで入れた技術は「なぜ必要か」を体で理解していないため、実務で応用できない。

## なぜBなのか

### 決定的な理由: 「重い処理」があること

PDF→画像変換や図面差分は必ず数秒〜数十秒かかる。すると、

| 起きる問題 | 必然的に必要になる技術 |
|---|---|
| 同期でやるとHTTPがタイムアウトする | キュー |
| ジョブが途中で落ちる | リトライ、冪等性 |
| 二重送信される | ジョブの状態機械 |
| ユーザーが待てない | ポーリング → SignalR |
| 結果が重い | Blob、署名付きURL、キャッシュ |

**すべてが業務要件から必然的に導出される。** これが学習題材として決定的に重要。

### 業務としての説得力

「最新版はどれか」問題は建設業の定番トラブル。
旧図面で施工してしまう事故は実際に起きており、改訂のたびに
「何が変わったか」を人力で見比べている現場は多い。

### AはBに含まれる

図面・ピン・指摘管理はBのMVPにそのまま入っている。
**「リビジョンという軸を1本足す」だけで学習密度が跳ね上がる構造。**

---

## 他案を外した理由

### E（検査テンプレート / 動的フォーム）— 次点

データ設計の学びは全案中トップ。
「柔軟性とクエリ性能のトレードオフ」「EAV vs JSONB vs テーブル分割」は
実務で最も判断力が問われるテーマ。オフライン同期は分散システムの入口。

**外した理由: 処理がすべて一瞬で終わる。**
非同期・スケーラビリティ・リアルタイムが一切出てこず、学習範囲がDB設計に偏る。

### C（施工写真管理）— 次点

ファイル転送の実務的難しさ（分割アップロード、署名付きURL直PUT、CORS、
サーバ経由 vs 直アップロードの判断）は Web実務で必ず必要になる知識。

**外した理由: ドメインが薄い。** Aggregateがほぼ1つで、設計判断の練習にならない。

### F / G / H — 単純CRUDで終わる

共通の弱点:

- 入力がテキストと数値だけ → ファイル管理を学べない
- 処理が即座に終わる → 非同期を学べない
- データ量が少ない → パフォーマンス設計を学べない
- 同時編集が起きない → 楽観的ロック・リアルタイムを学べない

### D / I — 複雑すぎる

共通の弱点:

- コア機能が動くまでに数ヶ月かかり、その間Web技術を一切学べない
- ライブラリに逃げると学習価値が消える

Dのガントチャート自作は沼。IのIFCパースは数百MBのファイルを扱う上、
3D特有の罠が多い。**Iはフェーズ4の発展課題として最適。**

### J（RAG）— 単体では薄い

SSEとベクタDBは学べるが、Web基盤の網羅性が低い。
**Bの1機能（類似指摘検索、指摘の自動要約）として組み込むのが正解。**

---

## 最終方針

**Bを幹にして、Cのアップロード技術とEの動的フォーム、Jのベクタ検索を
後から機能として足していく。**

1つのアプリで全技術テーマを網羅でき、
かつ各技術が「なぜ必要か」の文脈を持った状態で導入できる。

### 唯一の懸念と対策

差分検出の画像処理で沼る可能性がある。

**対策: フェーズ1では差分検出を作らない。**
PDF→PNG変換だけでも十分に「重い非同期処理」。
これでパイプラインの骨格を作り、動いてから差分検出に着手する。
