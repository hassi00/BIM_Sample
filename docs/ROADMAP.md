# 学習ロードマップ — 建設DX Webアプリ個人開発

最終更新: 2026-09-20

## このドキュメントについて

Web開発未経験の C# エンジニアが、個人開発を通じて
「Webアプリケーションを設計・判断できるエンジニア」になるための学習計画。

- 作るもの: **図面リビジョン管理 + 差分検出 + 指摘管理アプリ**（テーマ選定の経緯は [THEME.md](./THEME.md)）
- 重視するのは「完成」よりも **設計判断の経験**
- 方針: **小さく動かす → 痛みを感じる → 技術を足す**

## ステップ0（2〜3週間）: Webの「仕組み」を理解する

### 0-1. HTTPとブラウザ（最重要）

DevTools の Network タブを開いて、普段使うサイトの通信を実際に眺めるところから。

- [ ] リクエスト / レスポンス、メソッド（GET / POST / PUT / DELETE）
- [ ] ステータスコードの使い分け（200 / 201 / 204 / 400 / 401 / 403 / 404 / 409 / 500）
- [ ] ヘッダー（Content-Type, Authorization, Cookie）
- [ ] Cookie と localStorage の違い、なぜ認証で議論になるか
- [ ] **CORS** — 未経験者が100%ハマる。「なぜブラウザだけこの制約があるのか」を理解する
- [ ] ステートレスとは何か（サーバはリクエスト間で何も覚えていない）

**なぜ重要か**: Web開発の本質は「HTTPというステートレスなプロトコルの上に、いかに状態を作るか」。
ここが腹落ちすると、認証もキャッシュもAPI設計も全部つながる。

### 0-2. HTML / CSS / JavaScript

Reactの前に、**素のJSでDOMを触る小さいものを1つ作る**。

- [ ] 課題: HTML + JS だけでTODOリスト（フレームワークなし、100行程度）
- [ ] `document.querySelector`、イベントリスナ、`fetch`
- [ ] **なぜReactが生まれたのか**を体感する（手でDOMを書き換えるのが辛いと分かる）

JavaScript で押さえるもの:

- [ ] `const` / `let`、アロー関数、分割代入、スプレッド
- [ ] 配列メソッド（`map` / `filter` / `reduce`）← Reactで毎日使う
- [ ] 非同期（Promise, async/await）← C#のTaskと似ているので有利
- [ ] モジュール（import / export）

### 0-3. TypeScript

C#経験者なら1〜2日。ただし以下は意識して学ぶ。

- [ ] **構造的型付け**（C#の名前的型付けとの違い）
- [ ] union型、リテラル型
- [ ] 型推論、`unknown` と `any` の違い

## ステップ1（1週間）: 最小のフルスタックを1本通す

本番アプリを始める前に、**1つのデータをブラウザからDBまで往復させる**だけのものを作る。

```
React（入力フォーム）
  → fetch で POST /api/memos
    → ASP.NET Core のエンドポイント
      → EF Core
        → PostgreSQL（Dockerで起動）
      ← 保存結果
    ← JSON
  ← 画面に一覧表示
```

機能はメモの追加と一覧のみ。

- [ ] React + Vite + TypeScript のプロジェクト作成
- [ ] ASP.NET Core Web API プロジェクト作成
- [ ] docker-compose で PostgreSQL 起動（ローカルインストールしない習慣をつける）
- [ ] EF Core の Migration を1回実行する
- [ ] **CORSエラーに遭遇し、自力で解決する** ← これが目的の半分
- [ ] GitHub Actions で「ビルドが通るか」だけのCIを置く

## ステップ2（2週間）: Reactを「ちゃんと」学ぶ

ステップ1のメモアプリを拡張しながら学ぶ。

| 概念 | 理解すべきこと |
|---|---|
| コンポーネント | 関数がUIを返す。propsで親から子へデータが流れる |
| `useState` | 状態が変わると再レンダリングされる、という宣言的UIの中核 |
| 再レンダリング | いつ、何が起きているかを React DevTools で実際に見る |
| `useEffect` | **多用しない**。「外部システムとの同期」にだけ使う |
| リストと `key` | なぜkeyが必要か（差分検出の仕組み） |
| フォーム | 制御コンポーネント |

### WPF / MVVM 経験者への注意

「状態が変わるとUIが追従する」という発想は同じ。
ただし **ReactにはViewModelインスタンスが存在せず、毎回関数が丸ごと再実行される**。
ここを混同すると必ず混乱する。

### サーバ状態とクライアント状態を分ける（最重要）

- **サーバ状態**（APIから来るデータ）→ `TanStack Query` に任せる
- **クライアント状態**（モーダルの開閉、選択中のピン）→ `useState` / `Zustand`

全部 `useState` + `useEffect` でfetchすると、ローディング・エラー・キャッシュ・再取得の管理で破綻する。
**最初からTanStack Queryを使う。**

## ステップ3（7週〜）: 本番アプリのMVP開発

### 垂直スライスで作る

層ごとに作る（DB全部 → API全部 → 画面全部）のは**最も失敗しやすいやり方**。
何も動かない期間が長く、心が折れる。

```
スライス1: ユーザー登録 + ログイン（DB→API→画面まで通す）
スライス2: プロジェクト作成・一覧
スライス3: メンバー招待とロール
スライス4: 図面アップロード（まず同期版でいい）
スライス5: 図面表示（PDF.js + Canvas、ズーム / パン）
スライス6: ピン設置と指摘作成
スライス7: 指摘一覧・ステータス変更・コメント
── ここまででMVP完成。人に見せられる状態にする ──
スライス8: アップロードを非同期化（キュー導入）
スライス9: 進捗のリアルタイム通知（SignalR）
```

各スライスは**数日で終わる粒度**に切り、必ず「画面で動く」ところまで持っていく。

### MVPスコープ（これ以上入れない）

1. ユーザー登録 / ログイン / JWT
2. プロジェクト作成、メンバー招待、ロール付与
3. 図面PDFアップロード → ジョブ登録して即 202 を返す
4. ワーカーが PDF→PNG 変換 + サムネ生成 → Blobへ
5. フロントは処理中スピナー → ポーリングで完了検知
6. 図面表示（ズーム / パン）
7. クリックでピン設置 → 指摘作成（タイトル、説明、担当者、期限）
8. 指摘一覧 / ステータス変更 / コメント
9. Docker Compose（api / worker / db / redis / minio）

**意図的に外すもの**: リアルタイム、差分検出、AI、3D、ダッシュボード。すべてフェーズ2以降。

### ドメインモデル（初期案）

```
Project (Aggregate Root)
  └ ProjectMember (Role: Owner / Manager / Worker / Viewer)

Drawing (Aggregate Root)          ← 図面という「論理的な1枚」
  └ DrawingRevision (Entity)      ← Rev.A, Rev.B...
      - BlobKey, PageCount, Status(Uploaded/Processing/Ready/Failed)

Issue (Aggregate Root)            ← 指摘。Drawingとは別Aggregate
  - DrawingRevisionId
  - Position (VO: PageNo, X, Y ※正規化座標 0.0〜1.0)
  - Status (Open / InProgress / Resolved / Closed)
  - AssigneeId, DueDate
  └ IssueComment, IssueAttachment

ProcessingJob (Aggregate Root)    ← 非同期ジョブの状態
```

#### 設計上の「考えどころ」（ここが学習の本体）

- **座標は正規化座標（0.0〜1.0）+ ページ番号で持つ。**
  理由: ズーム倍率・レンダリング解像度・デバイスに依存しないため。
  これは実装テクニックではなく「ドメインの不変な事実は何か」という問い。
- **`Issue` を `Drawing` の子にしない。**
  ライフサイクルが独立し、Rev跨ぎで引き継がれるため。
  Aggregate境界 = トランザクション境界 = 同時更新の単位、という原則を実地で判断する。
- **`Status` 遷移はドメインメソッド（`issue.Resolve(userId)`）でしか変えられないようにする。**
  setter は private に。

### 技術スタックと選定理由

| 層 | 選択 | 理由 |
|---|---|---|
| FE | React + TypeScript + Vite | 情報量が最も多く、市場価値も高い |
| 状態管理 | TanStack Query + Zustand | サーバ状態とクライアント状態を分けて考える訓練 |
| PDF表示 | PDF.js を Canvas に自前描画 | ライブラリ任せだと座標変換を学べない |
| BE | ASP.NET Core | 既存の強み。ここは無理に新技術を使わない |
| DB | PostgreSQL | 「Webで使われる技術」を学べる。JSONB / 全文検索 / pgvector が後で効く |
| 認証 | まず自前 JWT + Refresh Token | Auth0等に逃げると認証設計を学べない。後でOIDCへ移行 |
| ストレージ | MinIO（ローカル）→ Azure Blob | S3互換で開発が楽、クラウド移行も容易 |
| 非同期 | Channel + BackgroundService → Redis + Hangfire | まず標準機能で作り、限界を感じてからミドルウェアへ |

## 「現場の開発方法」を個人開発で再現する

ここが実は一番価値がある。一人でも現場のやり方は再現できる。

### 1. GitHubで一人チーム開発

```
1. Issueを立てる（「#12 図面アップロード機能」）
2. ブランチを切る（feature/12-drawing-upload）
3. 小さくコミットする
4. Pull Requestを出す
5. 自分でレビューする（差分を読み直す）
6. CIが通ったらマージ
```

**一人でもPRを出す。** 自分のコードを差分として客観的に読む訓練になり、
現場のレビューで指摘される観点を先回りできるようになる。

コミットメッセージは Conventional Commits（`feat:` / `fix:` / `refactor:`）で統一。

### 2. CIを最初の1週間で作る

後回しにすると永遠にやらない。ステップ1の時点で GitHub Actions を置く。

```
push → ビルド → テスト → Lint → 型チェック
```

最初は「ビルドが通るか」だけでいい。緑のチェックマークが付く体験が習慣を作る。

### 3. テストを書く（全部は書かない）

| 優先 | 対象 | 理由 |
|---|---|---|
| 高 | ドメインロジック（ステータス遷移ルール等）の単体テスト | 速い、壊れにくい、価値が高い |
| 中 | APIの統合テスト（Testcontainers で本物のPostgresを起動） | 現場で最も投資対効果が高い層 |
| 低 | Reactコンポーネントのテスト | 変更が激しく壊れやすい |
| 最低 | E2E（Playwright） | 主要導線1〜2本だけ |

**Testcontainers は特に覚える価値がある。**
「インメモリDBでテストして本番で壊れる」という現場あるあるを回避する技術。

### 4. 環境を分ける

- ローカル（Docker Compose）/ 本番（クラウド）
- 接続文字列やAPIキーを**コードに書かない**
- ローカルは .NET User Secrets、本番は環境変数や Key Vault
- **現場の最低ライン**なので最初から守る

### 5. ログを最初から入れる

`Console.WriteLine` でデバッグする癖をつけない。Serilog で構造化ログを出す。

> 「なぜ動かないか」を print文で探す のが素人
> 「なぜ動かないか」をログとトレースで説明できる のが現場

### 6. ADR（設計判断の記録）を書く

`docs/adr/0001-why-postgresql.md` のように残す。
**「なぜこうしたか」を書けないなら、まだ理解していない証拠。**
設計できるエンジニアを目指すなら、これが最大の投資になる。

## 心構え

**分からないまま先に進むのを恐れない。** ただし以下2つだけは守る。

- 動いた時: **なぜ動いたか**を説明できるか確認する
- 動かない時: **エラーメッセージを読む**（未経験者は読まずに検索する）

## 到達目標

完走すれば、**Webアプリケーションのアーキテクチャを要件から技術選定まで一人で決められる**ようになる。

- 「この処理は同期か非同期か」を根拠を持って判断できる
- 「このデータはRDBか、JSONBか、Blobか、キャッシュか」を判断できる
- 認証と認可を分けて設計でき、ロールとリソース単位の権限を使い分けられる
- 障害時にログとメトリクスから原因を特定できる
- CI/CD と IaC で環境を再現できる
- クラウドのマネージドサービスを、コストと運用性を踏まえて選べる

建設DX側では、**図面のリビジョン管理・是正フロー・BIM連携という業界の中核課題を、
実装レベルで語れる**ようになる。

## 注意点（繰り返し読むこと）

1. **フェーズ1で技術を欲張らない。** マイクロサービス、CQRS、イベントソーシングは不要。
   モノリスで作り、痛みを感じてから分割を検討する。その判断過程こそが設計力。
2. **判断を記録する。** ADRを残す習慣が設計者への最短路。
3. **DDDを過剰適用しない。** 既にDDDを知っているからこそ、
   「どこにDDDを適用しないか」を学ぶフェーズ。CRUDで十分な箇所にAggregateを作らない。
4. **フロントに時間を割く。** 伸びしろはここ。
   バックエンドは慣れた領域なので、意識的に React / TypeScript / ブラウザAPI に投資する。
