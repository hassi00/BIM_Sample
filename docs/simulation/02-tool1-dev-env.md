| 問い | 自分の答え（AutoCADアドイン開発） | Web開発では |

| コードを何で書いたか | Visual Studio | **VS Code**（軽いエディタ。機能は拡張機能で足す） |
| 動かして確認する方法 | ビルド → AutoCAD で DLL を netload | 毎日の確認は**自分のPCでサーバーを動かし、ブラウザで `http://localhost:3000` などを開く**。保存すると数秒で反映（ホットリロード）。デプロイは「DLLを現場のPCに配る」に当たる |

### 講評

- 良い: Web は「サーバーやクラウドで動く」ので、netload に当たるのはデプロイ、と考えた（レッスン2）
- 足りない: デプロイは本番に置くこと。**毎日の動作確認はローカル（自分のPC）で動かす**のが普通
- VS Code を使う理由（Web向けの拡張機能が充実）は正解。他に、無料・軽い・1つで複数言語・Mac でも同じ、がある。チームの道具が揃うのは PM にも大事


`README.md` を VS Code で書いて保存し、PowerShell で `Get-Content README.md` を実行した。

### 出来事1: PowerShell を開き直す理由（PATH）

PowerShell は「コマンドをどのフォルダから探すか」の一覧（環境変数 PATH）を起動時に一度だけ読む。インストーラーが一覧に書き足しても、開いていた画面は古いまま。「入れたのに『認識されません』」の原因の定番。

### 出来事2: 文字化け

`Get-Content README.md` で日本語が化けた。`-Encoding UTF8` を付けると正しく表示された。

- 自分の予想:「UTF-8 で保存したが、PowerShell が Shift_JIS で読んでいる？」→ **正解**
- VS Code は UTF-8 で保存。Windows PowerShell 5.1 は何も指定しないと Shift_JIS として読む
- ファイルは壊れていない。同じデータを別のルール（文字コード）で読んだだけ
- 今の Web 開発の標準は UTF-8。Shift_JIS は古い Windows と Excel に残っている

## 場面1へのつなぎ: 報告書の出力で起きる事故

問い:「所長の事務所で、出力した検査結果を Excel で開いて手直しする。何が起きそうで、エンジニアに何を確認するか」

- 自分の答え:「文字コードを統一しないと、Web の表示や出力した報告書で文字化けが起こる」
- 良い: 文字化けが報告書でも起きると気づいた
- 足りない: **受け取る側（事務所の Excel）は統一できない**。「統一する」だけではエンジニアが動けない
- 具体的な事故: UTF-8 の CSV を Excel でダブルクリックすると化ける。開発者のPCでは気づかず、現場で初めて発覚する
- レッスン7（ファイル）:「作る側ではなく、受け取る側の環境で決まる」

## エンジニアに聞くべき質問

- 報告書の出力形式は何ですか（CSV / Excel / PDF）？
- CSV なら、Excel でダブルクリックして化けない形（BOM付き UTF-8）にしていますか？
- 大野所長の事務所と同じ Excel で開いて確認しましたか？
- 協力会社名や人名の「髙」「﨑」、「①」のような記号は正しく出ますか？

## 学び

| 学び | 内容 |
|---|---|
| **道具は Visual Studio 時代とほぼ同じ形** | 新しいのはターミナルと「ローカルでサーバーを動かしてブラウザで見る」流れ |
| **デプロイとローカル実行は別** | 毎日はローカル、本番に置くのがデプロイ |
| **「入れたのに動かない」はまず PATH** | ターミナルを開き直す |
| **文字化けは「書いたルールと読んだルールのずれ」** | ファイルが壊れたわけではない |
| **相手の環境は統一できない** | 報告書は「誰が・何で開くか」から決める。業務知識（事務所は Excel）が技術判断になる |
