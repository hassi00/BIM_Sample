# レッスン5: データ設計

学習日: 2026-09-24

**12回で最重要の回。** 権限とAPIの両方の性質を持ち、
さらに **既存データの移行** という逃げ場のない問題が加わる。

```
コードは書き換えられる。
データは、すでに存在してしまっている。
```

| | 変更のコスト |
|---|---|
| フロントのUI | 作り直せばいい |
| API | 契約。だが**足すのは安全** |
| **データ構造** | **既存データがあるので、足すだけでは済まないことがある** |

## 1. 固定値か、カスタマイズ可能か

「優先度を現場ごとに自由設定したい」で増えるもの：

| 増えるもの | 内容 |
|---|---|
| マスタテーブル | 種類を保存する場所 |
| **管理画面** | 追加・編集・並び替え・削除のUI（**画面1つ = 3〜8人日**） |
| 権限 | 誰が設定を変えられるのか |
| 並び順 | 「高・中・低」の順序をどう持つか（名前順では意味がない） |
| **使用中の削除** | 使われている優先度を消そうとしたら？ |
| 表示の色分け | 種類が違うと色も固定できない |
| 絞り込みUI | 選択肢が動的に変わる |
| **既存データ** | 設定変更時、過去の指摘の優先度はどうなる？ |

**工数は5〜10倍。** しかし本当の問題は工数ではない。

### 本当の問題: 横断集計ができなくなる

```
A現場: 「緊急・重要・通常」
B現場: 「S・A・B・C」
C現場: 「高・低」

→ 「全社で緊急案件は何件？」に永久に答えられない
```

**経営層が見たい数字が出せなくなる。**

> **必ず返す質問: 「全社で横断して集計したい数字はありますか？」**
> あるなら、自由設定にしてはいけない。

### 現実的な落としどころ

| 方式 | 内容 |
|---|---|
| **固定 + 表示名だけ変更可** | 内部は高中低。現場は呼び方だけ変えられる ← **優秀** |
| 固定 + 補助項目 | 優先度は固定。独自分類は「タグ」で自由に |
| 完全自由 | 横断集計を諦める |

**これはPMにしか提案できない解決策。**
エンジニアは「できます/できません」しか言えない。業務の落としどころを設計するのはPMの仕事。

## 2. 削除 —「消す」のか「使わなくする」のか

### 物理削除と論理削除

| | 内容 |
|---|---|
| 物理削除 | 本当に消す。**関連データが壊れる** |
| 論理削除 | `is_deleted = true`。データは残る |

作業員を物理削除すると、過去300件の指摘が「登録者：不明」になるか、
最悪**エラーで画面が開かなくなる**。

### 論理削除の代償

**すべてのクエリに「削除されていないもの」という条件が必要になる。**

```
❌ SELECT * FROM users
⭕ SELECT * FROM users WHERE is_deleted = false
```

**1箇所でも書き忘れると退職者が一覧に出る。**
レッスン3の権限と同じ「書き忘れで漏れる」構造。

### より良い設計: そもそも削除しない

建設業では**人は現場を渡り歩く**。再参加は普通に起きる。だから：

```
❌ ユーザーを削除する
⭕ プロジェクトへの参加を終了する
```

| | |
|---|---|
| **ユーザー** | その人。**永続。消さない** |
| **メンバーシップ** | 人 × 現場 の参加期間。**始まりと終わりがある** |

```
佐藤 × A現場  2025-04-01 〜 2026-03-31（終了）
佐藤 × C現場  2026-09-01 〜 （現在）
```

「削除」ではなく「**期間の終了**」としてモデル化すると：

- 過去の指摘が壊れない
- 再参加しても同じ人として扱える
- **「いつ誰が現場にいたか」が履歴として残る**（労務管理・監査で価値がある）
- A現場の画面には出ないが、C現場では出る

> **「削除機能をつけて」と言われたら必ず聞く:**
> 「**それは『存在を消す』ですか？ それとも『もう使わない状態にする』ですか？**」
>
> ほとんどの業務システムは後者。**そして両者は全く別の実装になる。**

### 表示の問題

| 案 | 評価 |
|---|---|
| 「佐藤」 | 現役と区別がつかない |
| **「（退職）佐藤」** | **実務で最も使われる** |
| 「削除済みユーザー」 | 監査で困る。誰がやったか分からない |

### 個人情報（法務が絡む）

```
論理削除 = データは残っている
  ↓
「個人情報を削除してください」と本人から要求されたら？
```

**論理削除だけでは応えられない。** 対応は匿名化：

```
氏名・連絡先を「退職者A」に置き換える
指摘との紐付け（ID）は残す → データは壊れない
```

**匿名化と削除は別物。** この違いを知っているPMは重宝される。

## 3. 後から項目を追加する

### 任意なら安全（APIと同じ原則）

```
⭕ 「空でもよい（NULL許容）」項目として足す
   → 既存50万件は全部NULL
   → 一瞬で終わる。データの書き換えが発生しない
```

### 必須にすると危険

```
❌ 必須項目として足す
   → 既存50万件に何か入れる必要がある
   → 50万行を全部書き換える
   → その間テーブルがロックされ、アプリが止まる
```

50万件なら数十秒、5000万件なら**数時間**。その間サービス停止。

> **API:  「足すだけなら安全」**
> **データ: 「任意で足すなら安全。必須にするのは危険」**

### NULL許容にした時の別問題

```
確認者が NULL の指摘が50万件。これは何を意味する？

案1: まだ確認していない（未確認）
案2: そもそも確認が不要な指摘
案3: 機能追加前のデータ。概念自体が存在しなかった
```

**区別がつかない。** すると：

```
「未確認の指摘は何件？」→ NULLを数えると50万件
→ でも実際の未確認は3件
```

**ダッシュボードの数字が意味をなさなくなる。**

> **項目追加時に必ず決めること:**
> 「**既存のデータでは、この項目はどういう扱いにしますか？**」
>
> - 空のまま（区別がつかない問題を受け入れる）
> - 一括で何かを入れる（**移行作業が発生**）
> - 「この日以降のデータのみ対象」という運用ルールにする ← **現実的な解が多い**
>
> **これを決めるのはエンジニアではなくPM。**

## 持ち帰り: データ設計で必ず聞くこと

| 質問 | 何を防ぐか |
|---|---|
| **全社で横断集計したい数字はありますか？** | 自由設定による集計不能 |
| **「削除」は存在を消す？ 使わなくする？** | 関連データの破壊 |
| **同じ人が再び参加することはありますか？** | 削除ではなく期間終了でモデル化 |
| **既存データでは、この新項目はどう扱いますか？** | 意味不明なNULLの山 |
| この項目は必須にしますか？ | 移行時のサービス停止 |
| 個人情報の削除要求に応える必要は？ | 匿名化の設計が要る |
