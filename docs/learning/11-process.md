# レッスン11: 開発プロセスとCI/CD

学習日: 2026-10-06

**ゴール: エンジニアの1日の流れを知り、無茶なスケジュールを引かない。**

## 「修正は30分です」はリリースまでの時間ではない

```
修正             30分
自動テスト        15分
レビュー          待ち時間込みで数時間
ステージング確認   1時間
→ リリース可能は早くて夜、普通は翌日
```

**前日の夕方に入る修正は、一番危険な修正。** 確認時間が足りず、焦りで新しいバグを生む。

### リリース判定はPMの仕事

| 選択肢 | 選ぶ時 |
|---|---|
| 延期する | バグが重大（データ破損、権限漏れ） |
| **バグを残してリリース** | 影響が小さく回避策がある。翌週に修正 |
| その機能だけ外してリリース | 問題が特定機能に閉じている |

> **判断の材料は修正時間ではなく「そのバグで何が起きるか」。**
> 聞く: 「そのバグで、ユーザーには何が起きますか？ データは壊れますか？」
> 「30分で直るならやって」は判断の放棄。

## コードが本番に届くまで

```
プルリクエスト → 自動テスト → レビュー → マージ → ステージング確認 → 本番反映
                └────── CI ──────┘          └──────── CD ────────┘
```

- **CI**（継続的インテグレーション）: 合流させるたびに自動で確認
- **CD**（継続的デリバリー／デプロイ）: 確認済みのものを自動で届ける

### 見落としやすい待ち時間: レビュー

| 段階 | 待ち時間 |
|---|---|
| 自動テスト | 数分〜十数分。機械なので読める |
| **レビュー** | **他人の手が空くまで。半日〜2日。読めない** |

PMができること:
- レビュー担当と**返す目安（例: 1営業日以内）**を決める
- リリース直前の週はレビューする人の時間を空ける
- プルリクエストを**小さく**するよう促す

## 小さく頻繁にリリースする

| | 3ヶ月に1回 | 毎週 |
|---|---|---|
| 1回の変更量 | 数百箇所 | 数箇所 |
| 問題が出たら | **原因が分からない** | ほぼ特定できる |
| 元に戻すなら | 3ヶ月分 | 1週間分 |
| リリース作業 | 年4回なので**手順を忘れる** | 慣れている |

建設で言えば「最後にまとめて検査」より「工程ごとに検査」。

**CI/CDの目的は楽をすることではなく、小さく頻繁に出せる状態を作ること。**

### スケジュールの引き方が変わる

```
❌ 「6ヶ月後に全機能をリリース」
⭕ 「毎週何かがリリースされ、6ヶ月後に全機能が揃っている」
```

2週目からパイロット現場に触ってもらえる。
レッスン6の「使ってみないと分からない」問題がここで解消できる。

## 持ち帰り

| 論点 | PMとして |
|---|---|
| 修正時間 ≠ リリースまでの時間 | 「30分で直る」でスケジュールを判断しない |
| **リリース判定はPMの仕事** | 「そのバグで何が起きるか」で決める |
| レビューは人の時間 | 担当と返却の目安を決める |
| 小さく頻繁に出す | トラブルが減り、現場に早く触ってもらえる |
