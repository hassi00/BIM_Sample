学習日: 2026-10-02

## ピークで考える

建設現場の朝：

```
7:50 朝礼。全員が今日の指摘を確認
8:00 KY活動。図面を開いて危険箇所を確認
8:10 作業開始。担当の指摘を開く
```

50現場 × 数十人が、同じ15分間に、同じ操作をする。

| | 意味 |
|---|---|
| 平均負荷 | 1日の利用を24時間で均したもの |
| **ピーク負荷** | 一番混む瞬間 |

```
1日5,000回 → 平均は1時間200回
実際は朝8時台に3,000回 → ピークは平均の15倍
```

**システムは平均ではなくピークに耐える必要がある。**

> 「1日何人使いますか？」ではなく
> **「一番混む時間帯に、同時に何人が使いますか？」**

建設現場のピーク：朝礼・KY・昼休み明け・夕方の日報。**業務を知っている人にしか分からない。**

## 利用者が25倍になったら、費用は何倍か

| 項目 | 倍率 | 理由 |
|---|---|---|
| サーバ費用 | **25倍以下** | 1台に余裕がある。ピーク時だけ増やせる（オートスケール） |
| **保存費用** | **25倍以上。毎年増え続ける** | 利用者数 × **時間**に比例 |
| 転送量費用 | ほぼ25倍 | 見る人に比例。CDNで対策 |
| 表示速度 | **設計次第** | インデックスがあればほぼ変わらない。なければ大幅に遅くなる |

### 保存費用が最大の落とし穴

```
1年目:  2現場分
2年目: 50現場分 + 1年目の分
3年目: 50現場分 + 1〜2年目の分 ...
```

**データは消えずに溜まり続け、費用は絶対に下がらない。** しかも建設業には保存義務がある。

> クラウド費用の試算は**5年目まで**出す。
> **古いデータをどうするか**（安い保存領域へ移す、期限で削除）を最初に決める。

### サーバ費用とステートレス

```
ピークに合わせて常に大きなサーバ → 1日の大半は無駄
ピークの時間だけ自動で増やす    → 安い
```

レッスン1の「ステートレスなサーバは使い捨てにできる」がここで効く。

## パイロットでは性能は分からない

| | パイロット | 全社展開 | パイロットで分かるか |
|---|---|---|---|
| 同時利用者 | 数十人 | 千人以上 | **分からない** |
| データ量 | 2,000件 | 20万件 | **分からない** |
| 操作の種類 | 同じ | 同じ | 分かる |

2,000件ならインデックスがなくても速い。問題が出ないまま全社展開し、そこで初めて遅くなる。

**パイロットは「機能が業務に合うか」を確かめる場。性能は確かめられない。**

### 負荷試験

```
本番規模のデータ（20万件）を人工的に作る
千人が同時に操作する状況を人工的に作る
速度を測る
```

> **「パイロットで問題なかった」は、性能が問題ないことを意味しない。**
> 全社展開の前に、**負荷試験の期間と費用**を計画に入れる。見積もりから抜けやすい。

## 持ち帰り: 必ず聞くこと

| 質問 | なぜ |
|---|---|
| **一番混む時間帯に、同時に何人使いますか？** | ピークで設計する |
| **データは何年保存しますか？ 5年後の費用は？** | 保存費用は増え続ける |
| 大きいファイルを何人が見ますか？ | 転送量 |
| 3年後に何件になりますか？ | インデックス設計 |
| **全社展開の前に、本番規模で試験しますか？** | パイロットでは分からない |
