# 学習記録

## 学習の目的（2026-09-20 改訂）

転職先で **Webアプリ開発のPM** として動く。Web開発の実務経験はない。

- **第一目標**: エンジニアから信頼を得られる最低限の知識を持つこと
- **第二目標**: 自分で手を動かす可能性にも備えること

順番は「全体像を先に、コードは後」。
先に全体像があると、コードを書く時に「今どこを触っているか」が分かる。

## 設計方針 — 信頼を失うPM / 得るPM

エンジニアがPMに不信感を持つ瞬間は、だいたい決まっている。

| 信頼を失う言動 | 裏にある無理解 |
|---|---|
| 「ボタン1個足すだけでしょ？」 | 画面・API・DB・テスト・移行の連鎖が見えていない |
| 「なんでそんなに時間かかるの？」 | 見えない作業（テスト、リリース、移行）を知らない |
| 「とりあえず後で直せばいい」 | DB設計とAPI設計は後から直すのが一番高い |
| 「セキュリティは後回しで」 | 後付けできない種類のものがあると知らない |
| 「動いてるから大丈夫」 | 運用・監視の概念がない |
| 仕様を口頭で変え続ける | 変更がどこまで波及するか分かっていない |

逆に、信頼されるPMは **「分かっていないと自覚していること」が明確**。

> 「ここは私の理解が浅いので、判断材料をください」
> 「これは後から変えると高くつく箇所ですか？」

この2つが言えるだけで、エンジニアの態度は変わる。

## カリキュラム（全12回）

各回に「**エンジニアに聞くべき質問リスト**」を付ける。
知識そのものより、現場で使える問いの形で持っておく方が実用的なため。

| # | テーマ | これが無いと信頼を失う場面 | 状態 |
|---|---|---|---|
| 1 | HTTPとステートレス | 「サーバ増やせばいいんでしょ」が的外れになる時 | ✅ [01-http.md](./01-http.md) |
| 2 | フロントとバックの分離 / 見積もりの読み方 | 「この機能どっち側の作業？」が判断できず工数配分を誤る | ✅ [02-frontend-backend.md](./02-frontend-backend.md) |
| 3 | 認証と認可 | 「権限まわりちょっと変えて」が実は大工事、を知らない | |
| 4 | API設計と画面の関係 | 1画面にAPIが何本必要か見積もれない（スケジュール崩壊の最大要因） | |
| 5 | データ設計 | 「あとでカラム足せばいい」が通じない場面を理解する | |
| 6 | 変更コストの非対称性 | どの決定を急ぎ、どれを後回しにできるかの判断軸 | |
| 7 | ファイル・画像・図面の扱い | 建設DXで必ず来る要件。見積もりを外しやすい代表格 | |
| 8 | 同期と非同期 | 「なんで待たされるの？」に答えられる。UX要件の書き方が変わる | |
| 9 | セキュリティの勘所 | 「後回しで」と言ってはいけないものを見分ける | |
| 10 | 性能・スケール・コスト | 「1万人使っても大丈夫？」に判断材料を持って臨める | |
| 11 | 開発プロセスとCI/CD | エンジニアの1日が分かる。無茶なスケジュールを引かなくなる | |
| 12 | 運用・監視・障害対応 | リリースは終わりではない、が体で分かる | |

**想定: 1回1時間 × 12回 = 約12時間**

## 今回カバーしないと決めたこと

- JavaScript / TypeScript の文法
- React の書き方
- CSS
- SQLの書き方

**理由**: これらは「知らなくても信頼は失わない」領域。
PMがReactを書けなくても誰も困らないが、
データ設計の変更コストを知らないPMは実際にプロジェクトを壊す。

必要になったら、12回の後に [ROADMAP.md](../ROADMAP.md) のステップ1（最小フルスタック）で扱う。

## 進め方

1. 先に説明しない。まず問題を出す
2. 自分で考えて答える。間違いが一番学べる
3. 答え合わせと、そこから派生する話だけ
4. 手を動かす課題は「**予想してから実行**」— 予想と違った時に記憶に残る

調べて答えた場合は「調べた」と明記する（自力の推測か調査かで返し方を変えるため）。
