# レッスン3: 認証と認可

学習日: 2026-09-22

**権限は、PMが最も安易に要求しがちで、最も高くつく領域。**

## 用語

| | 認証 (Authentication / AuthN) | 認可 (Authorization / AuthZ) |
|---|---|---|
| 問い | **あなたは誰ですか？** | **あなたは何をしてよいですか？** |
| 例 | ログイン、パスワード | この指摘を編集できるか |
| 失敗時 | **401** | **403** |
| 例え | 建物の入館証を見せる | その部屋に入れるか |

## 認証より認可が圧倒的に大変

| | 認証 | 認可 |
|---|---|---|
| 作るもの | ログイン、ログアウト、PW再設定 | **すべての機能に影響する判断ロジック** |
| 仕様変更 | ほぼ来ない | **運用開始後に無限に来る** |
| 既製品で済むか | **済む**（Auth0, Entra ID, Google） | **済まない。業務ごとに違う** |
| 工数 | 5〜10人日で固定 | **青天井** |

> 「ログイン機能を作る」は見積もれる。
> 「**権限管理を作る**」は要件が固まるまで見積もれない。
>
> エンジニアが「権限の要件を詰めさせてください」と言ったら、
> **引き延ばしではなく、最も重要な作業。**

## なぜ「ロールを3つ足す」では済まないのか

ロール（RBAC）は **人の属性だけ**で決める。
しかし現実の要望は、それ以外の材料を必要とする。

| 要望 | 判断に必要なもの |
|---|---|
| 田中さんだけ例外的に編集可 | **その人が誰か**（ロールを超えた個別指定） |
| A工区の担当者だけ見れる | **対象データの属性**と人の属性の照合 |
| 協力会社は自社が関わる指摘だけ | **人と対象の関係** |
| 完了済みは編集不可 | **対象データの状態** |
| 承認を通してから公開 | **手続きの進行状況** |

現実の権限は「**人 × 対象 × 状態 × 関係**」で決まる。

### 3つの方式

| 方式 | 判断基準 | 例 |
|---|---|---|
| **RBAC**（ロールベース） | 人の役割 | Manager は編集できる |
| **ABAC**（属性ベース） | 人と対象の属性 | 工区が一致すれば見れる |
| **ReBAC**（関係ベース） | 人と対象の関係 | 担当者本人なら編集できる |

実際のアプリはこれらの組み合わせになる。
**だから権限は青天井になる。**

## 最重要の分岐: ロールは「どこに」付くのか

```
案A: ユーザーにロールを1つ      田中 = Manager
案B: プロジェクトごとにロール    田中 × プロジェクトA = Manager
                                田中 × プロジェクトB = Worker
```

**建設業では案Bが必須**（現場ごとに立場が変わるため）。

| | 案A | 案B |
|---|---|---|
| データ構造 | ユーザーテーブルに1カラム | **中間テーブルが必要** |
| 権限チェック | 「この人のロールは？」 | 「**この人の、このプロジェクトでの**ロールは？」 |
| 工数 | 小 | **2〜3倍** |
| 後から変更 | — | **ほぼ作り直し** |

> **必ず聞かれる質問:**
> 「ユーザーの権限はシステム全体で1つですか？ プロジェクトごとに変わりますか？」
>
> 即答できると信頼される。**間違えると後で作り直し。**

## 権限を後付けすると何が起きるか

| 箇所 | 影響 |
|---|---|
| 全API | 1本ずつ判定を追加。**漏れたら情報漏洩** |
| 全一覧画面 | クエリに条件追加。**性能も変わる（インデックス再設計）** |
| データ構造 | 所属情報がなければ**テーブル追加とデータ移行** |
| 画面 | ボタンの表示制御を全画面に |
| テスト | **ロール × 機能の組み合わせ分** |

4ロール × 30機能 = 120通りの検証をやり直すことになる。

> 「とりあえず全員が全部見れる状態で作って、後から権限を足して」
> = 「家を建ててから基礎を入れて」

## Secure by Default

```
❌ 各APIで「この人は見ていいか？」をチェック
   → 新しいAPIで書き忘れたら、そこから漏れる

⭕ DBに問い合わせる時点で、見ていいものしか取らない
   → 書き忘れようがない
```

### IDOR — 情報漏洩事故の代表格

一覧は絞り込んでいるのに、`GET /api/issues/1201` に直接アクセスすると見れてしまう。
URLのIDを1つずつ変えれば他人のデータが全部見える。

**Insecure Direct Object Reference (IDOR)。実際に非常によくあるバグ。**

> **PMとして: 権限のテストで「一覧に出ないこと」だけ確認して満足しない。**
> **「URLを直接叩いても見えないか」を必ず確認項目に入れる。**

## 持ち帰り: 要件定義で必ず聞くこと

| 質問 | なぜ |
|---|---|
| **権限は全体で1つ？ プロジェクトごとに変わる？** | 構造が2〜3倍変わる |
| **「この人だけ例外」は発生しますか？** | ロールだけでは足りなくなる |
| **データの状態で権限は変わりますか？** | 判断が複雑化 |
| **社外の人（協力会社・発注者）は使いますか？** | **設計が根本的に変わる** |
| 権限は誰が設定？ 管理画面は要る？ | **画面が増える** |

## 見積もりの目安

| 要望のパターン | 難易度 |
|---|---|
| ロールが数個、全体で固定 | 軽い |
| プロジェクトごとにロールが変わる | **中〜重** |
| 対象データの属性で変わる（工区、会社） | **重い** |
| 個別の例外を設定できる | **非常に重い。管理画面も必要** |
| 承認フローがある | **別機能として見積もる** |

## 絶対に言ってはいけない

- 「権限は後から足して」
- 「とりあえず全員見れる状態で」
- 「ロールを1つ追加するだけでしょ？」
