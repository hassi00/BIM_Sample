# レッスン6: 変更コストの非対称性

学習日: 2026-09-25

**これまでの5回を「判断の道具」に組み直す回。**
実務で最も使う能力 —「要件定義の優先順位を自分で引く」。

```
「いつ決めるか」を決めるのが、PMの仕事。
```

## 判断基準

> **後から足せるものは、後回しでいい。**
> **後から「変える」しかないものは、最初に決める。**

もう一つの言い方：

> **「すでに動いているものに影響するか？」**
> 影響しない → 後回し / 影響する → 最初に決める

通知を足しても既存の指摘登録は変わらない。
権限を足すと全機能に手が入る。

| | 後から | 例 |
|---|---|---|
| 土台 | **変えるしかない** | 権限、データ構造、利用シーン |
| 契約 | **段階移行が必要** | API |
| 機能 | **足せる** | 通知、レポート、画面追加 |

## 最初に決めるべきもの

| 項目 | 理由 |
|---|---|
| **権限の構造** | 土台。後から足せない（下記） |
| **データモデル** | 既存データは新仕様を知らない（レッスン5） |
| **ステータスの遷移ルール** | 権限 + データ構造の両方に触る |
| **データ移行の有無** | 既存データの形が新しい構造を制約する |
| **利用シーン（どこで誰が使うか）** | 機能ではなく**前提条件**。後から変えられない |
| **図面バージョン管理の有無** | 指摘が「図面」でなく「図面のバージョン」に紐づくか |

## 後回しでいいもの

| 項目 | 理由 |
|---|---|
| 通知 | 既存機能に手を入れずに足せる |
| レポート・帳票出力 | 読み取るだけ。影響が小さい |
| ダッシュボードの項目 | 同上 |
| 画面の細かいUI | 作り直せる |

## 権限が変えにくい3つの理由（レッスン3の復習）

| 理由 | 何が起きるか |
|---|---|
| ① **全機能に入り込む** | 修正箇所が機能の数だけある |
| ② **書き忘れが漏洩になる** | エラーが出ないので**バグに気づけない** |
| ③ **データ構造が必要になる** | 所属・会社・工区の情報が要る → レッスン5の問題に発展 |

①だけなら「大変」で済む。**②と③があるので「危険」になる。**

> 「権限は後から足して」
> = 「全機能を作り直して、かつ情報漏洩のリスクを取って、かつ既存データの移行もやって」

## 罠1: スマホ対応は「後回し」にできない

現場監督と作業員は、**現場でスマホから**指摘を登録する。そうでなければ使われない。

| 論点 | 影響 |
|---|---|
| 画面の作り方 | PC向けUIはスマホで使えない。**作り直しに近い** |
| 通信回数 | 電波が悪い場所での5回通信 = 5秒待ち。**API設計に跳ね返る** |
| 写真 | スマホ写真は1枚5MB。圧縮、再送、複数枚 |
| **オフライン** | 後付けは**アプリの作り直しレベル** |
| 図面表示 | 小さい画面のズーム・ピンチは別実装 |

### ただし「決める」と「作る」は違う

```
最初に決めること: 「スマホで使う。現場で登録する。オフラインは非対応とする」
最初に作ること  : スマホで動く画面（オフラインは作らない）
```

**方針を決めておけば後から作れる。方針を決めずにPC前提で作ると、後から変えられない。**

> **「どこで、誰が、どんな状況で使うか」は機能ではなく前提条件。**
> 機能は後から足せるが、前提条件は後から変えられない。

## 「決める」の3段階

| 段階 | 内容 | 例 |
|---|---|---|
| **確定する** | 今、完全に決める | 権限の構造、データモデル |
| **方針だけ決める** | 詳細は後、方向性は今 | 「スマホで使う。オフラインは将来検討」 |
| **決めない** | 後でいい | 通知メールの文面 |

```
❌ 「通知の仕様を全部決めてください」→ 決まらない、会議が止まる
⭕ 「通知は作ります。誰に何を送るかは後で。
     ただし『メールだけか、アプリ内通知も要るか』だけ今決めてください」
```

後者は5分で決まる。それだけ決まれば実装は進む。

> **PMの腕の見せどころは、「今決めるべき最小の問い」に分解すること。**

## 「使ってみないと決められない」と言われたら

### ① まず聞くべき質問

> **「今、その業務をどうやって管理していますか？」**

システムが無くても**業務はすでに存在している**。Excel、紙、LINE、口頭。
そこには現状のステータス、更新する人、完了の判断者が**すでにある**。

**「決められない」のは業務が未定だからではなく、「画面がイメージできない」から。**
業務を聞けば答えは出る。相手は業務のプロなので。

| 聞く内容 | 引き出せるもの |
|---|---|
| **「今のExcelを見せてください」** | **現状のステータスと運用がそのまま分かる** |
| 「これを付けるのは誰ですか？」 | 権限 |
| 「間違えた時はどうしていますか？」 | **遷移のルール（戻せるか）** |
| 「完了かどうかは誰が判断しますか？」 | 承認フローの有無 |
| 「困っていることは何ですか？」 | 本当に解くべき課題 |

**「Excelを見せてください」は要件定義で最も強力な一手。** 100回のヒアリングより情報量がある。

### ② 叩き台を持っていく

人は**ゼロから設計するのは苦手**だが、**目の前の案にダメ出しするのは得意**。

```
❌ 「どうしますか？」          → 「分からない」
⭕ 「こうしますが、いいですか？」 → 「いや、そこは違う」← 情報が出る
```

**作るのはエンジニアではなくPM。** エンジニアは業務を知らない。

### ③ 要素に分解してコストを示す

「ステータス」と一口に言っても中身は複数あり、変更コストが違う。

| 要素 | 後から変えられるか |
|---|---|
| **呼び方**（「完了」→「是正済」） | **変えられる。今決めなくていい** |
| 種類の数 | **変えにくい。** 既存データが影響を受ける |
| **遷移のルール** | **変えにくい。** 権限と絡む |
| 誰が変えられるか | **変えられない。** 権限の土台 |
| 履歴を残すか | **変えられない。** データ構造 |

**「全部決めてください」ではなく「この3つだけ今決めてください」に分解する。**

### ④ 「後で」には期限と値段を付ける

| 決めること | 例 |
|---|---|
| いつまでに決めるか | 「実装に入る◯月◯日までに」 |
| 決まらなかったらどうするか | 「こちらで仮決定して進めます」 |
| **後で変えるコスト** | 「その後の変更は◯人日かかります」 |

**「変えられない」ではなく「有料です」と言う。**
無料だと思っているから「後で」と言う。

### まとめた言い方

> 「後から調整、できます。**ただし2種類あります。**
>
> **名前を変えるだけなら、いつでも無料でできます。**
> **種類を増やす・遷移を変えるのは、リリース後だと◯人日かかります。**
>
> なので、**種類と遷移だけ、◯月◯日までに決めましょう。**
> 叩き台は私が作ります。それを見て、違うところを言ってください。」
