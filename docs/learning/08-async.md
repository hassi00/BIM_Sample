# レッスン8: 同期と非同期

学習日: 2026-09-27

**ゴール: 「なぜ待たされるのか」を説明でき、UX要件を正しく書けるようになる。**

```
非同期は「待たせない」ための解決策。
しかし、その代わりに「状態の管理」という新しい仕事を生む。
```

## 同期と非同期

| | 意味 | ユーザー体験 |
|---|---|---|
| **同期** | 終わるまで画面が待つ | くるくる → 結果 |
| **非同期** | 受け付けだけして、処理は裏で | 「受け付けました」→ 後で通知 |

## 何秒まで待たせていいか

| 時間 | ユーザーの感覚 |
|---|---|
| 0.1秒 | 瞬時。操作と結果が直結している |
| 1秒 | 思考が途切れない限界 |
| **10秒** | **注意が保てる限界。超えると別のことを始める** |

**10秒を超えるなら非同期にする。**

| 処理 | 想定時間 | 判断 |
|---|---|---|
| 指摘1件登録 | 0.3秒 | 同期 |
| 一覧の絞り込み | 1秒 | 同期 |
| 写真1枚 | 5秒 | **非同期寄り**（現場の電波では30秒になる） |
| 図面変換 | 3分 | 非同期 |
| Excel出力 | 30秒 | **非同期**（下記の技術的理由） |
| 月次レポート | 5分 | 非同期 |

### 30秒の処理を同期でやってはいけない技術的理由

サーバやロードバランサには「30秒以上かかるリクエストは切る」設定がよくある。
**成功しているのにユーザーにはエラーが出る**という最悪の事態になる。

> **時間の見積もりは「最良の条件」ではなく「最悪の条件」で考える。**
> 社内Wi-Fiで5秒でも、現場の4Gでは30秒。データが10倍になれば処理も10倍。

## 重い処理の画面設計（3分かかる図面変換）

- ボタンを押したら元の画面に戻れる。**他の作業ができる**
- **画面を閉じても変換は続く**
- 失敗したら、通知やステータス表示で分かる
- **「3分ほどかかります」と最初に伝える**

待ち時間の不満は、時間そのものより **「いつ終わるか分からない」** ことから来る。

### ユーザーにやり直させない

```
❌ 「10分経っても終わらなければやり直してください」
   → 実は1回目は遅れていただけで生きていた
   → 2回目も走る → 同じ図面が2つできる

⭕ システムが10分で自動タイムアウト判定
   → 自動で1回リトライ
   → それでも失敗したら「失敗しました」と通知
   → ユーザーには「再実行」ボタンだけ見せる
```

**「リトライしていいか」はユーザーに判断させず、システムが判断する。**
（レッスン1の冪等性）

## 非同期にすると「状態」が生まれる

同期なら「成功」か「失敗」しかない。非同期にすると、その間が生まれる。

```
受付済み → 待機中 → 処理中 → 完了
                          ↘ 失敗 → リトライ中 → 完了
                                              ↘ 最終失敗
```

この状態を **DBに記録し、画面に出し、変化を通知する** 必要がある。全部が工数。

## 重複には2種類ある

| 重複の種類 | 例 | 対策 |
|---|---|---|
| **意図的** | 同じ図面をもう一度上げた | 確認ダイアログ（上書き or 別名） |
| **意図しない** | 電波が悪くて反応がなく、二度押し | **冪等キー** |

意図しない重複では確認ダイアログは出せない（2回目の時点で1回目がまだ処理中）。

```
ボタンを押した瞬間に一意の受付番号を発行
→ 2回目のリクエストも同じ受付番号
→ サーバは「この番号はもう処理中」と判断して無視
```

## 失敗に「誰が」気づくか

```
18:00 監督が図面をアップして帰宅
18:05 変換失敗
翌朝  監督が出社して気づく → 朝礼で使う予定の図面がない
```

| 誰が | 何を知るべきか |
|---|---|
| **ユーザー** | 自分の図面が失敗した。再実行できる |
| **運用者** | **失敗が多発している。システムに問題がある** |

1件の失敗はユーザーの問題かもしれない（壊れたPDF）。
**10件連続なら、システムの問題。**
気づく仕組みがないと、**現場からの電話で初めて知る**。（→ レッスン12）

## 処理待ちが溜まったら

1件3分 × 100件 = **5時間待ち**。100件目の人にとっては壊れているのと同じ。

| 対策 | トレードオフ |
|---|---|
| **処理する人（ワーカー）を増やす** | **クラウド費用が増える** |
| 優先度をつける | 誰が「急ぎ」を決める？ |
| 待ち時間を表示する | 解決はしないが不満は減る |

> 「朝8時に全現場が一斉に図面をアップする」と分かっていれば、その時間帯だけワーカーを増やせる。
> **「いつ、どのくらいの量が来るか」を業務から予測するのはPMの仕事。**

## 非同期にすると必要になるもの

| 必要になるもの | 工数 |
|---|---|
| ジョブの状態管理（DB） | 中 |
| 状態表示の画面 | 中 |
| **完了・失敗の通知** | 中〜大 |
| 自動リトライ | 小〜中 |
| **二重実行の防止（冪等キー）** | 中 |
| **失敗の監視（運用者向け）** | 中 |
| 処理能力の調整（ワーカー数） | インフラ |

> **「重い処理はバックグラウンドで」は、1行の要件ではなく、7つの機能。**
> 見積もりに「非同期処理」と1行しか書いていなかったら、中身を聞く。

## 持ち帰り: 非同期処理で必ず聞くこと

| 質問 | なぜ |
|---|---|
| **最悪の条件（現場の電波、10倍のデータ）で何秒ですか？** | 同期/非同期の判断 |
| 完了・失敗はユーザーにどう伝えますか？ | 通知の工数 |
| **二度押しされたらどうなりますか？** | 冪等性 |
| **失敗が多発したら、誰がどうやって気づきますか？** | 運用監視 |
| **一番混む時間帯はいつで、何件来ますか？** | ワーカー数とコスト |
| 自動リトライはしますか？ 何回まで？ | 無限リトライ防止 |
