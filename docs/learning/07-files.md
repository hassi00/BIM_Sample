# レッスン7: ファイル・画像・図面の扱い

学習日: 2026-09-26

**建設DXで避けて通れず、かつ見積もりを最も外しやすい領域。**

## 写真10枚（50MB）を不安定な電波でアップロードすると

### 技術的な失敗

| 何が起きるか |
|---|
| **電波が切れて中断** → 最初からやり直し（49MB送った後でも） |
| **タイムアウト** → 「30秒以上のリクエストは切る」設定で途中切断 |
| **サイズ上限で拒否** → サーバやLBに「1リクエスト10MBまで」の制限 |
| **メモリ不足** → 50MBを一度に載せると、同時10人で500MB |
| **スマホのブラウザが落ちる** |
| **写真が横倒し** → iPhoneは**EXIFの向き情報**を見ないと回転が狂う |
| **HEIC形式** → iPhoneの標準形式。そのままではブラウザで表示できない |

最後の2つは定番のバグ。「写真がなぜか横向き」「iPhoneだけ表示されない」。

### 運用・業務の失敗（PMの領域）

| 何が起きるか |
|---|
| **ギガが減る** → 「このアプリ、パケット食う」と嫌われる |
| 送信中に画面を閉じる → **「送ったつもり」が発生** |
| 送れたか分からない → **同じ写真を何度も送る** |
| 上司に「まだ登録されてない」と言われる → **信頼を失う** |

> **ファイルアップロードの失敗は、機能の失敗ではなく、システムへの信頼の失敗になる。**
> 一度そうなると現場は紙に戻る。

## 対策（それぞれが工数）

### ① クライアント側で圧縮する（最重要）

```
5MB → ブラウザ内で縮小 → 500KB
50MB → 5MB
```

**10倍速くなり、失敗率が激減する。**

**どこまで縮めていいかはPMが決める。**

| 用途 | 必要な画質 |
|---|---|
| 「ここが汚れている」の記録 | 低くてよい |
| **ひび割れ幅の確認** | **高画質必須** |
| **工事写真（法定の提出物）** | **圧縮不可。原本保存が必要な場合も** |

**最後が建設業特有。** 法定の工事写真は改ざん防止の観点から加工が禁止されていることがある。
**知らずに圧縮する設計にすると、使えないシステムになる。**

### ② 分割して送る（チャンクアップロード）

```
50MB を 1MB × 50個に分けて送る
→ 途中で切れても続きから再開できる
→ 進捗が正確に出せる
```

**「途中から再開できる」は、電波が不安定な現場では決定的。**

### ③ サーバを経由しない（署名付きURL）

```
❌ スマホ → 自社サーバ → ストレージ
   サーバが50MBを受け止める。同時10人で死ぬ

⭕ スマホ → ストレージに直接
   サーバは「ここに置いていいよ」という許可証を発行するだけ
```

**クラウド時代の標準的な作り方。** サーバの負荷とコストが劇的に下がる。

### ④ 待たせない

```
写真の送信中も指摘の入力は続けられる
バックグラウンドで送る
完了したらチェックマーク / 失敗したら再送ボタン
```

**「送ったつもり」を防ぐのは技術ではなくUIの設計。**

## どこに保存するか — DBではなくストレージ

| | DBに入れる | ストレージに置く |
|---|---|---|
| 一覧取得 | **画像まで一緒に読む**ので激重 | 情報だけ軽く取れる |
| バックアップ | DBが巨大化。**復旧に何時間も** | 分けて管理できる |
| 配信 | すべてサーバ経由 | **CDNから直接配信できる** |
| コスト | DBのストレージは**高い** | オブジェクトストレージは**安い** |

**コスト差は10倍以上。**

> **原則: DBには「データ」を、ストレージには「ファイル」を。**
> **DBに入れるのは、ファイルの置き場所（パス）だけ。**

### 分離したことで生まれる問題

DBとストレージが別なので、整合性が取れないことがある。

```
ストレージに保存成功 → DBへの記録が失敗
→ 誰からも参照されない写真がストレージに残る（孤児ファイル）

DBに記録あり → ストレージにファイルなし
→ 画像が表示されない
```

**「孤児ファイルの掃除」という地味な運用作業が必要。**
見積もりに入っていないことが多い項目。

## 図面は写真とは別問題

80MBのPDFは、スマホではまず開けない。

### 解決策: 事前に変換しておく

```
アップロード時（1回だけ、バックグラウンドで）
  PDF 80MB
    → 各ページを画像に変換
    → 「タイル」に分割（地図アプリと同じ仕組み）
    → 解像度別に用意（縮小表示用、拡大用）

閲覧時
  画面に見えている部分のタイルだけ読む → 一瞬で表示
```

**Google Mapsと同じ発想。** 日本全国の地図を一度に読み込んだりしない。

→ これが**レッスン8（同期と非同期）**につながる。
「アップロードした瞬間には見れない。変換が終わるまで待つ」という設計が必要になる。

### 100人が同時に開いたら

```
80MB × 100人 = 8GB を一気に配信
→ サーバの回線が詰まる
→ クラウドの転送量課金が跳ね上がる
```

**対策はCDN（配信網）。**
図面を各地のサーバにコピーしておき、利用者に近い場所から配信する。
**図面は一度アップしたら変わらない**ので、CDNと相性が良い。

> **クラウドのコストは「保存」より「転送」で膨らむ。**
> 大きいファイルを多人数が見るシステムでは、**転送量の試算**が必要。

## 建設DX特有の論点（業務知識が効く）

| 論点 | 判断が必要なこと |
|---|---|
| **法定の工事写真** | 圧縮・加工してよいか。原本保存の義務はあるか |
| **図面の機密性** | 施工図は機密。**URLを知っていれば誰でも見れる**状態になっていないか |
| **保存期間** | 竣工後の保管義務。**何年？ 誰が費用を持つ？** |
| ファイル名 | 「A棟_2F_平面図_Rev.C_20260901.pdf」のような命名規則が現場にある |
| **容量の見積もり** | 1現場あたり図面何枚、写真何枚？ 50現場だと何TB？ |

### 容量試算はPMの仕事

```
1現場: 図面200枚 × 30MB     = 6GB
       写真5000枚 × 500KB    = 2.5GB
       計 約9GB

50現場 = 450GB
5年保存 = ...
```

**これがクラウド費用の見積もりの根拠になる。**
「10年保存が必要」と後から言われると費用が跳ね上がる。

## 持ち帰り: ファイルを扱う機能で必ず聞くこと

| 質問 | なぜ |
|---|---|
| **この写真は圧縮してよいですか？** | 法定写真・計測用途なら不可 |
| **原本を保存する義務はありますか？** | 容量とコストが変わる |
| **保存期間は何年ですか？** | 長期コストの根拠 |
| 1現場あたり何枚くらいですか？ | 容量試算 |
| 電波が悪い場所で使いますか？ | 分割送信・再開の要否 |
| **この図面を同時に何人が見ますか？** | 転送量とCDNの要否 |
| 図面は機密ですか？ | URL直接アクセスの防止が必要か |
