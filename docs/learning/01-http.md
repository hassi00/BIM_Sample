学習日: 2026-09-20 / 形式: 問いに自分で答えてから答え合わせ（アクティブラーニング）

## 導出の流れ

自分で考えて辿り着いた連鎖。この順番で思い出せれば、Web認証の全体像は再構築できる。

```
サーバは状態を持てない（スケールしないから）
  → だからブラウザに持たせる
    → でもブラウザのデータは改ざんできる
      → だから改ざんを「防ぐ」のではなく「検知」する
        → ハッシュだけでは破られる（攻撃者も同じ計算ができる）
          → ハッシュに秘密鍵を混ぜる = HMAC = JWTの署名
            → でも丸ごとコピーされたら署名では防げない（リプレイ攻撃）
              → 期限を切る + 通信を暗号化する + 盗まれにくい場所に置く
                → HttpOnly Cookie か localStorage か、という「判断」
```

## 1. ステートレス

サーバがユーザーごとの状態をメモリに持つと、

- サーバを増やした時、2回目のリクエストが別のサーバに届いて状態を引き継げない
- スティッキーセッション（同じユーザーは同じサーバへ）で回避できるが、
  - そのサーバが落ちると状態が全部消える
  - **負荷分散のために増やしたのに、負荷分散にならない**

→ **ステートレスなサーバは「使い捨て」にできる。**
落ちたら捨てる、負荷が上がったら増やす、減ったら消す。
これがクラウド（オートスケール、コンテナ）が成立する前提条件。

ステートレスは思想ではなく、**運用を楽にするための実利的な選択**。

## 2. 改ざん検知 → HMAC

ユーザーの手元にあるデータはすべて改ざん可能。防ぐのは不可能なので検知する。

```
❌ 署名 = SHA256(データ)              誰でも再計算できる → 破られる
⭕ 署名 = SHA256(秘密鍵S + データ)     攻撃者はSを知らない → 作れない
```

検証：サーバが手元のSで再計算し、送られてきた署名と比較する。

| 方式 | 鍵 | 用途 |
|---|---|---|
| HMAC (HS256) | 1つの秘密鍵をサーバだけが持つ | 発行も検証も自分（本プロジェクトはこれ） |
| 公開鍵署名 (RS256) | 秘密鍵で署名、公開鍵で検証 | 発行者と検証者が別（OIDC, Auth0） |

**JWT = 「データ + HMAC署名」を Base64 で繋げただけ。** 魔法ではない。

## 3. リプレイ攻撃と3つの対策

改ざんせず丸ごとコピーして使われると、署名は正しいので検知できない。

| 観点 | 対策 |
|---|---|
| 時間 | 有効期限（JWTの `exp`）。短くしすぎると再ログインが頻発 → Refresh Token で補う |
| 経路 | HTTPS (TLS)。本番でHTTPを使ってはいけない理由 |
| 保管場所 | HttpOnly Cookie にすると JS から読めない → XSSで盗めない |

### 保管場所のトレードオフ（正解がない）

| 保管場所 | XSSで盗まれる | CSRF |
|---|---|---|
| localStorage | 盗まれる | 影響なし |
| 通常のCookie | 盗まれる（`document.cookie`） | 受ける |
| HttpOnly Cookie | **盗まれない** | **受ける** → `SameSite` で対策 |

Cookieは「ブラウザが自動で付けてくれる」のが利点だが、
**攻撃者のサイトからのリクエストにも自動で付く**のが弱点（CSRF）。

→ localStorage vs Cookie 論争の正体はこれ。技術の優劣ではなく判断の問題。

## 4. URL とサーバの分岐

```
github.com/hassi00        → Content-Type: text/html
api.github.com/users/...  → Content-Type: application/json
```

**ホスト名で分岐している。ホストが違う = 物理的に別のサーバ群。**

画面配信とAPIでは求められる性能もスケールの仕方も違うので、分けた方が都合がいい。

### 本プロジェクトでの選択肢（後で決める）

```
案1: myapp.com                      画面もAPIも同じ
案2: myapp.com / api.myapp.com      GitHub方式
案3: myapp.com/ と myapp.com/api/   パスで分離
```

### ここに CORS が埋まっている

ホストが違うと、ブラウザは「別のサイト」と見なしてリクエストをブロックする。

理由：銀行にログイン済みの状態で攻撃者のサイトを開いた時、
そのサイトのJSが自由に `bank.com/api/transfer` を叩けたら成立してしまう攻撃があるから。

**CORSは嫌がらせではなく、この攻撃を防ぐための仕組み。**

## 5. Content-Type は「指定」ではなく「申告」

サーバはもう中身を送っているので、これはラベル。

通信路の上では JSON も HTML も画像もただのバイト列。
**受け取った側がどう解釈すべきかを知るために、ラベルが要る。**

### `X-Content-Type-Options: nosniff`

ブラウザには昔「Content-Typeを信じず中身から推測する」機能があった（MIME sniffing）。

```
攻撃者が .txt をアップロード（中身は実はJavaScript）
サーバは text/plain と申告
ブラウザが「JSっぽい」と勝手に判断して実行 → XSS
```

`nosniff` = 「勝手に推測するな、申告を信じろ」。

→ **ファイルアップロード機能を作る本プロジェクトでは他人事ではない。**

## 6. ブラウザは実行環境である（今回の最大の学び）

GitHubのプロフィールページを計測したら、HTML内の外部ファイル参照は **107個**。
HTML本体と合わせて**最低108回の通信**が発生する。

予想は「1回」だった。なぜ外れたか：

```
1. ブラウザ → GET /hassi00
2. サーバ  → HTMLを返す（この時点で画面は真っ白）
3. ブラウザがHTMLを解析し、<link> <script> <img> を発見
4. ブラウザが自律的に107回リクエストを飛ばす
5. 全部揃って画面が完成
```

**この107回を指示したのは自分でもサーバでもない。ブラウザが自分で判断している。**

→ ブラウザは単なる表示ソフトではなく、HTMLを解釈して通信する**実行環境**。

## 7. 画面は誰が作るのか（WPF脳からの切り替え）

```
WPF:  [ アプリ ] ← 画面もロジックもデータアクセスも全部1つの中

Web:  [ ブラウザ ]                    [ サーバ ]
        HTML/CSS/JS を実行     ←→      JSONを返すだけ
        ↑ 画面の組み立てはここ
```

| 誰が | 何を |
|---|---|
| React（自分が書くJS） | 画面を組み立てる。**ブラウザの中で動く** |
| ASP.NET Core | **JSONだけ返す。HTMLは作らない** |

ASP.NET Core は `api.github.com` 側の役割だけを担当する。
HTMLを配信するのは別の仕組み（開発中は Vite、本番は静的ホスティング / CDN）。

> サーバがHTMLを組み立てる方式（Razor Pages、Next.jsのSSR）も実在し、間違いではない。
> 今回は Web特有の技術を学ぶ目的で、あえて完全に分離した構成を選ぶ。

## 環境メモ（PowerShell）

- `grep` は無い → `Select-String`
- `/dev/null` は `NUL`
- `curl` は `Invoke-WebRequest` のエイリアスのことがある → **`curl.exe` と書く**

```powershell
# レスポンスヘッダーだけ見る
curl.exe -s -D - -o NUL https://api.github.com/users/hassi00 | Select-String "content-type"

# HTML内の外部ファイル参照を数える
(curl.exe -s https://github.com/hassi00 | Select-String '<(script|link|img)[^>]*(src|href)=' -AllMatches).Matches.Count
```
