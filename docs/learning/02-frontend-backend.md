# レッスン2: フロントとバックの分離 / 見積もりの読み方

学習日: 2026-09-21

## 第1部: 「絞り込み機能の追加 = 5人日」の内訳

見た目の作業（UI追加、条件を渡す、結果を返す）は **1〜1.5人日**。
残りの3.5人日は、PMからは見えない。

| # | 作業 | 工数 | PMから見えるか |
|---|---|---|---|
| 1 | 要件の詰め（複数選択可？ 未割当は？ URLに残す？） | 0.3 | ❌ |
| 2 | API仕様の変更（パラメータ追加、既存条件との組み合わせ） | 0.3 | ❌ |
| 3 | **DBインデックス追加と実行計画の確認** | 0.5 | ❌ |
| 4 | バックエンド実装（フィルタ + **権限との併用**） | 0.5 | △ |
| 5 | フロント実装（UI、状態管理、URL反映） | 0.7 | ⭕ |
| 6 | **既存機能との組み合わせ確認**（ソート・ページング・他の絞り込み） | 0.5 | ❌ |
| 7 | エッジケース（0件表示、担当者が削除済み、大量選択） | 0.4 | ❌ |
| 8 | 自動テスト作成 | 0.6 | ❌ |
| 9 | **コードレビューと指摘対応** | 0.7 | ❌ |
| 10 | 動作確認・リグレッションテスト・リリース | 0.5 | ❌ |
| | **合計** | **5.0** | |

### 削ると何が起きるか

| 削ると | 結果 |
|---|---|
| インデックス（3） | リリース後に「一覧が重い」と炎上 |
| 権限併用（4） | **情報漏洩** |
| 組み合わせ確認（6） | 「ソートしてから絞り込むと壊れる」バグ |
| テスト（8） | 次の改修で気づかず壊す |
| レビュー（9） | 品質が属人化し、後で大きな手戻り |

### コードレビューは他人の時間

レビュー待ち・指摘対応で1〜2日溶ける。しかも**エンジニア本人にはコントロールできない**。
PMが最も見落とす工数。

## 第2部: インデックス

10万件から「担当者=田中」を探す時、素直にやると全件を1件ずつ確認する（フルスキャン）。
本の索引と同じ仕組みを作るのが**インデックス**。

```
インデックスなし: 数秒〜数十秒
インデックスあり: 数ミリ秒
```

- **インデックスはタダではない。** 書き込みが遅くなり、容量も食う
- だから「全項目で絞り込めるように」は、エンジニアにとって重い要求
- ハッシュインデックスは等値比較のみ。範囲検索には使えないので一般には B-tree

## 第3部: 権限は「土台」であって「機能」ではない

```
❌ 絞り込んだ後に権限チェック → エラーを返す
⭕ そもそも常に「自分が見ていいもの」だけを対象にしている
   → 権限外で絞り込んだら、単に0件になる
```

| 方式 | 問題 |
|---|---|
| 機能ごとに権限チェックを書く | **書き忘れた機能から漏れる**。機能が増えるほど危険 |
| 土台で常にフィルタする（行レベルセキュリティ） | 新機能を作っても自動的に守られる |

**権限設計は「あとで足す」ができない。土台の作り方の問題だから。**
「とりあえず権限なしで作って後から追加」は、作り直しに近い。

### 403 か 404 か

「存在するが権限がない」時、403を返すと**そのIDが存在することが漏れる**。
攻撃者はIDを総当たりして存在する一覧を作れる。だからあえて404にする設計もある。

**正解はない。** セキュリティと分かりやすさのトレードオフ。
これをエンジニアに丸投げせず一緒に決められるPMは信頼される。

## 第4部: フロント / バックの分け方

| # | 機能 | どちら | 理由 |
|---|---|---|---|
| 1 | 期限が近い順に並べる | **バック** | フロントでやるには全件必要。ページングと両立しない |
| 2 | 期限切れを赤字表示 | フロント | 見せ方だけ |
| 3 | 必須チェック | 両方 | 目的が違う（親切 / 防御） |
| 4 | ステータス変更 | 両方 | |
| 5 | 完了できるのは担当者だけ | 両方 | フロントはボタンを隠すだけ。**強制はバック** |
| 6 | 削除確認ダイアログ | フロント | |
| 7 | PDF→画像変換 | バック | |

### 判断基準

> **「嘘をつかれたら困ること」は、すべてバックエンド。**

フロントはユーザーの手元で動く = 改変できる = **嘘をつける**。

もう一つの言い方：

> **真実はどこにあるか。** 真実がサーバにあるなら判断もサーバでする。
> フロントにあるのは真実のコピーと、見せ方だけ。

### バリデーションは重複ではない

| | フロント | バック |
|---|---|---|
| 目的 | **親切** | **防御** |
| 無いと | 体験が悪い | **不正データが入る** |
| 省略可能か | 可 | **絶対に不可** |

**「フロントでチェックしてるからバックは要らない」は間違い。**
curlで直接APIを叩けば画面は迂回できる。

### 隠れた罠: 時計

「期限切れかどうか」をフロントで判断すると、ユーザーがPCの時刻を変えれば変わる。
表示だけなら問題ないが、**判断（編集可否など）はサーバの時計で。**

### 並び替えの例外

全件が最初から手元にある規模（100件程度）ならフロントでよい。
→ 判断基準は**データ量**。

> **聞くべき質問: 「この一覧、将来どのくらいの件数になりますか？」**

## 第5部: 1画面に必要なAPI

### APIは「機能ごと」ではなく「リソースごと」

```
❌ /api/issues/filter-by-status
   /api/issues/filter-by-assignee     ← 組み合わせの数だけ必要になり破綻

⭕ GET /api/issues?status=open&assignee=42&sort=dueDate&page=3
```

絞り込み・並び替え・ページングは、すべて1本のGETのパラメータ。
**「絞り込みを1つ足す = APIを1本足す」ではない。**

### 指摘一覧画面の実際

| 通信 | 本数 |
|---|---|
| 指摘一覧（絞り込み・ソート・ページング込み） | 1本 |
| 担当者の選択肢 | 1本 |
| ステータスの選択肢 | 0本（固定値はフロントに持たせる） |
| ログインユーザー情報・権限 | 1本 |
| **サムネイル画像** | **表示件数分（50本）** |

**API種類は3本。しかし実通信は50回超。**

> 「サムネイル出したい」= 1画面に数十回の通信が増える。
> 一覧が重い原因はたいていこれ。遅延読み込みは**追加の実装工数**であってタダではない。

### 画面数からの概算

```
1画面 ≒ API 1〜3本 + フロント実装 + テスト ≒ 3〜8人日
```

単純なCRUD画面は下限、図面ビューアのような特殊なものは別枠。

例：20画面のアプリ × 5人日 = 100人日 → 1人なら5ヶ月。
**「20画面を2ヶ月で」は無茶**と即断できる。

## 持ち帰り: 見積もりを受け取った時の質問リスト

数字を疑うためではなく、**リスクを掘るため**の質問。

| 質問 | 何が分かるか |
|---|---|
| この工数にテストとレビューは含まれていますか？ | **含まれない見積もりは必ず遅れる** |
| 既存のどの機能に影響しますか？ | 隠れた作業量 |
| このデータは将来どのくらいの件数になりますか？ | 性能リスク |
| 権限まわりで考慮が必要な点は？ | セキュリティリスク |
| **一番不確実なのはどの部分ですか？** | **見積もりのブレ幅** |
| 後から変更が高くつく判断はこの中にありますか？ | 今決めるべきこと |

### 言ってはいけない言葉

| ❌ | なぜ |
|---|---|
| 「ボタン1個でしょ？」 | 見えていない4.3人日を否定している |
| 「テストは後でまとめて」 | 後のテストはコストが数倍 |
| 「とりあえず動けばいい」 | 技術的負債の発注宣言 |
| 「権限は後から足して」 | **土台の作り直しを要求している** |
| 「フロントでチェックしてるからバックは不要」 | 画面は迂回できる |

### 代わりに言うべきこと

> 「この5日のうち、**一番読めない部分**はどこですか？」
>
> 「削るとしたら何が削れて、**その代わり何を諦めることになりますか？**」

「削れ」ではなく「削るとしたら何を諦めるか」と聞く。
判断をPMが引き受ける姿勢が伝わる。
