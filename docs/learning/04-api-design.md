# レッスン4: API設計と画面の関係

学習日: 2026-09-23

**ゴール: 設計書のAPI一覧を見て、地雷を見つけられるようになる。**

## 悪い設計の例

```
POST /api/createIssue
POST /api/updateIssue
POST /api/deleteIssue
POST /api/getIssueList
POST /api/getIssueListByAssignee
POST /api/getIssueListByStatus
```

問題は3つある。

### ① 動詞がURLに入っている

```
❌ POST /api/createIssue        「作る」がURLに入っている
⭕ POST   /api/issues            URLは「何に対して」だけ
   PUT    /api/issues/1201       「何をするか」はメソッドで表す
   DELETE /api/issues/1201
```

**URLは名詞（リソース）、操作はHTTPメソッド。**

createIssue方式だと、新機能のたびに名前を発明することになる
（create / add / new / register …）。人によってバラバラになり、一覧を見ても把握できない。

> **設計レビューで聞く: 「命名規則は統一されていますか？」**

### ② 参照系が全部POST

`GET` にはHTTPの仕組みとして特別な扱いがある。

| GETなら使える | POSTだと |
|---|---|
| **ブラウザ・CDNのキャッシュ** | 効かない |
| **URLの共有・ブックマーク** | できない |
| 戻るボタン | 警告が出る |
| リトライの安全性（冪等） | **二重登録のリスク** |
| アクセスログでの分析 | 中身が見えない |

```
「この絞り込み結果を部下に共有したい」
GET  /api/issues?status=open&assignee=42  → URLを送れば済む
POST → 不可能
```

> **「一覧の状態をURLで共有したい」は後から来ると高くつく。**
> GETなら自然にできるが、POST設計だと作り直しに近い。

### ③ 組み合わせ爆発（最大の地雷）

```
getIssueListByAssignee
getIssueListByStatus
  ↓ この先
getIssueListByDueDate
getIssueListByAssigneeAndStatus
getIssueListByAssigneeAndStatusAndDueDate
...
```

条件が5種類あれば組み合わせは31通り = **API 31本**。

正解：

```
GET /api/issues?assigneeId=42&status=open&dueBefore=2026-10-31
```

1本で済む。条件が増えてもパラメータが増えるだけ。

> **設計レビューで最も価値のある指摘:**
> 「この先、絞り込み条件が増えたらAPIも増えていく設計になっていませんか？」

## リソース単位か、画面単位か

指摘詳細画面（基本情報・担当者・写真・コメント・履歴）を作る時。

| 立場 | 主張 |
|---|---|
| フロント | この画面専用API 1本。通信1回で済む |
| バック | リソースごとに5本。他画面で使い回せる |

### 原則はリソース単位

**画面は変わりやすい。リソースは変わりにくい。**
変わりにくいものを土台にした方が、変更に強い。

### ただしフロントの言い分にも実害の根拠がある

```
指摘詳細を開く → API 5回
現場でスマホ、電波が悪い、1回1秒 → 画面が出るまで5秒
```

**建設現場のアプリでは致命的。**
通信回数は、電波の悪い場所で直接UXに跳ね返る。

### 実務の答え: BFF

```
土台   : リソース単位のAPI（変更に強い、使い回せる）
その上 : 画面単位のAPI（必要な画面だけ）
```

**Backend For Frontend (BFF)。**
最初から全画面に作るのは過剰。**遅くて困った画面だけ**後から足す。

> **PMの判断:**
> 「リソース単位で作る。ただし**現場でスマホを使う画面**は通信回数を確認して、
> 必要なら専用APIを検討する」
>
> **「現場でスマホ」という業務条件を持ち込めるのはPMだけ。**

## API は契約である

「レスポンスの項目名を変えたい」が難しい理由は、
**使っているのが自社のフロントだけではない**から。

| 利用者 | 変更したら |
|---|---|
| 自社Webフロント | 一緒に直せる。**これは楽な方** |
| **スマホアプリ** | **ユーザーが更新するまで古いまま動き続ける** |
| 他社との連携 | **相手のシステムが壊れる** |
| 社内バッチ | 誰も覚えていない。**深夜に静かに壊れる** |
| Excelマクロ、RPA | **存在すら把握されていない** |

スマホアプリが最悪。審査に数日、ユーザーの更新に数週間。
**その間、新旧両方が動いている。**

### 現実的な変え方

| 方法 | 内容 |
|---|---|
| 両方返す | 新旧の項目を共存させる |
| **Expand-Contract** | 新項目追加 → 利用側を移行 → 旧項目を削除 |
| バージョニング | `/api/v1/` と `/api/v2/` を併存 |

**どれも一発では変えられない。**

> 「APIの項目名、変えるだけでしょ？」は**言ってはいけない言葉**。
>
> 見積もりでAPI変更が重く見えたら聞く:
> **「このAPIは、今どこから使われていますか？」**

## 後から変えるのが高いものの共通点

| | 理由 |
|---|---|
| 権限（レッスン3） | **全機能の土台**だから |
| API（レッスン4） | **外部との契約**だから |
| データ設計（レッスン5） | **両方**だから |

**「最初に決めるべきこと」と「後で決めていいこと」を見分けるのがPMの一番大事な判断。**
（→ レッスン6のテーマ）

## 持ち帰り: 設計レビューで使う質問

| 質問 | 何を見抜けるか |
|---|---|
| 命名規則は統一されていますか？ | 設計の一貫性 |
| **絞り込み条件が増えたら、APIも増える設計ですか？** | **組み合わせ爆発** |
| 参照系は GET になっていますか？ | キャッシュ・URL共有の可否 |
| **このAPIは、将来どこから使われますか？** | 変更コストの見積もり |
| 現場でスマホを使う画面はどれ？ 通信は何回？ | **UXの実害** |
| 一覧の状態をURLで共有する要望はありますか？ | 今決めないと高くつく |
